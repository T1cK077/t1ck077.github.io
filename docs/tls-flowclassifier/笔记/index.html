Step 0.2 定「研究的协议边界」#

  • ✅ TLS 1.3 only
  • ❌ 不做 TLS 1.2 对比（可写背景，不做实验）
  • ❌ 不碰 QUIC / HTTP3
  • ❌ 不解密、不看 SNI、不看证书

📌 论文可说：

Step 0.3 定「一条 flow 是什么」#

  • 五元组： (src IP, dst IP, src port, dst port, protocol)
  • 超时时间： 60 秒无数据即结束

📌 原因：

  • 够简单
  • 文献常见
  • 不易被质疑

Phase 1 · 数据收集#

1.1 抓包环境#

  • 使用pyshark进行抓包

📌 为什么？

  • 可自定义抓取类型
  • 可自定义生成文件

过程：

  • 项目开始使用过滤器如下：

  • 后改为：

  • 注意到无法正常抓取期望数据包及流，原因如下：

    • 0x0304 确实是 TLS 1.3 的版本号，但 某些客户端/服务端在握手时可能还会用 TLS 1.2（0x0303）
    • display_filter 太严格，导致每个 TLS 1.3 相关流里匹配的包极少（通常只有 1–4 个：ClientHello + ServerHello + 少量 Finished/ChangeCipherSpec/Application Data）

  • 这个条件只匹配：

    • ClientHello/ServerHello 中明确声明支持 TLS 1.3 的包
    • 握手完成后 record.version = 0x0304 的加密数据包

  • 但一个完整 TLS 1.3 会话的前 30 个包里，满足这个条件的往往只有少数几个（握手包少，后续数据包如果还没大量传输，就匹配不上）。

  • 结果：大多数流只有 1–5 个包，自然达不到 10 个包的门槛。

  • 所以，做出如下核心改动：

    • 把 display_filter 改成 tcp.port == 443（最宽松，能抓到完整 TLS 流量，包括 TLS 1.3 的握手和后续数据包）
    • 去掉 if not hasattr(pkt, 'tls'): 的限制（因为 display_filter 已经保证有 TLS 相关流量）
    • 保留 MIN_PACKETS_PER_FLOW = 10（现在包数会多很多，流长度会变长，能轻松超过 10）

  • 改动后效果显著

1.2 确认流量#

  • 通过脚本生成的.pacp文件，设定TLS过滤器后观察到大部分流量都是 TLS 1.3，说明：

    • 当前采集的数据高度符合研究主题（基于深度学习的 TLS 1.3 加密流量分类）
    • 放宽到 tcp.port == 443 的采集方式是正确的：既抓到了完整流（长度足够长），又保持了很高的 TLS 1.3 纯度（大部分包/流都协商成了 1.3）
    • 少量混入的 TLS 1.2 比例很低，对模型影响几乎可以忽略（本科论文完全接受，甚至很多论文都不额外过滤）

  • 数据误差处于可接受范围内
